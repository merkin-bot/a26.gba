# GBA, DSSMM card, and SD harness

The harness has three independent layers:

1. **GBA system:** mGBA executes the kernel/plugin GBA code and models GBA CPU, memory, timers, video, DMA, and input.
2. **Flash card and kernel:** the matching DSSMM kernel runs and interacts with a per-model card profile. Do not merge different card mappings or kernel builds into one generic profile.
3. **SD storage:** each card profile reads a block image containing that card's matching kernel, the A26 plugin, and the Atari test ROM. The runner also loads the matching kernel as the cartridge image. FAT/filesystem operations must cross the emulated card's SD interface; a host FAT image check alone does not prove this path.

The six target profiles and exact DSSMM kernel release tags/artifacts are listed in `cards.json`. Kernels are maintained in [voluptuary/dssmm](https://github.com/voluptuary/dssmm); the earlier untagged audit snapshot `f6350776f07eba91ba2ffa34c6833d85f348f2a1` is not current release validation.

## EZ-FLASH source boundary

The exact-pinned EZ kernel sources share an SD sector transaction shape: halfword command writes through `0x09FE0000`, `0x08000000`, `0x08020000`, `0x08040000`, address/count at `0x09600000`/`0x09620000`/`0x09640000`, completion at `0x09FC0000`, status/data aperture `0x09E00000`, and control at `0x09400000`. Their FatFs glue chunks transfers by up to four sectors and DMA-copies through the 2 KiB data aperture. `ezflash_sd_model` validates the four-write unlock order, maps the sector/count request to a raw image, and supports the kernel's staged write payload. `ezflash_mgba_sd` implements this as an explicitly synthetic path with configurable ready status and no physical card latency. No SuperCard SD protocol is reused. DE and Original OMEGA use the shared page write; BLUE adds explicit OS/game mode in its page write and a flash-access preparation step. See [`docs/provenance/ezflash-source-audit.md`](../docs/provenance/ezflash-source-audit.md) for source locations, handoff behavior, and fixture limits.

`ezflash-mgba-trace-smoke` exercises a **passive GBA memory-callback trace hook**. It delegates every callback to mGBA unchanged and records selected accesses. The pinned mGBA DMA service uses these same callbacks and sets `GBA.performingDMA`. The smoke runs four-word channel-3 DMA probes into and out of the `0x09E00000` software data aperture, compares transfer hashes and DMA scheduling/wait-cycle fields with an untraced core, and verifies callback restoration on detach. This exercises mGBA's GBA DMA path, not an EZ card: source reads still use mGBA's original cartridge behavior, and no EZ response, mapping, or SD image is emulated.

`ezflash-sd-model-test` checks multi-sector reads, byte order, staged write payload before command commit, image bounds, and the selected synthetic status. `ezflash-mgba-sd-smoke` sends read and write transcripts through mGBA GBA bus callbacks against a temporary raw image, verifies callback cycle counts, exercises ARM LDM/STM, and checks ROM-page buffer mapping/restoration. `ezflash-mgba-runner` executes matching built DE, Original OMEGA, or BLUE kernels against separate FAT images and reports data/command totals plus a framebuffer hash. In the 300-frame fresh-image baselines, DE and BLUE read 154 sectors and wrote 30; Original OMEGA read 100 and wrote 30; all had zero image-model failures and rendered the same initial menu framebuffer. A controlled fresh EZ DE run with PocketNES and Snail Maze completed 2,500 GBA frames, read 803 blocks and wrote 216, and rendered the control screen (`ABA1E9FDDE9F1C85`); details are in [`docs/provenance/pocketnes-control.md`](../docs/provenance/pocketnes-control.md). The synthetic path separately models SD blocks, source-shaped PSRAM pages, and S71 NOR commands. At the source-observed `0x0200` ROM-page commit, the adapter mirrors PSRAM into mGBA's `GBAMemory.rom` because mGBA instruction fetches bypass the wrapped bus callbacks; it restores the original kernel bytes on remap. This is a host-emulator adaptation, not evidence of physical EZ wiring. `A26_EZ_TRACE_PC=1` prints guest PC and last SD LBA/count/direction; `A26_EZ_TRACE_EWRAM=<aligned address>` prints adjacent EWRAM words; `A26_EZ_TRACE_REGS=1` prints final CPU registers. Synthetic card response is status zero with no card latency. Fixture launch suites provide separate source-level launcher/metadata coverage with storage/boot seams mocked. EZ plugin handoff is established only for this synthetic DE path; physical PSRAM/NOR/card behavior, timing, shell return, and the other EZ lanes remain `UNVERIFIED`.

## Current SuperCard model boundary

The SuperCard adapter uses SuperFW Build769 source in `rom_boot.S`, `src/supercard_driver.c`, `src/loader.c`, and `src/supercard_io.S`. The source uses `0x09FFFFFE` for all three board builds: mode bit 0 selects SDRAM versus firmware/flash, bit 1 enables the SD interface, and bit 2 controls SDRAM writes. The GBA boot stub copies 1 KiB from `0x08000000` to IWRAM and executes it; the plugin loader stages the plugin/game at `0x08000000` and launches in SDRAM mode. The mGBA adapter switches CPU cartridge fetches between the original kernel ROM in firmware mode and model SDRAM in SDRAM mode. This common fetch mapping is source-supported for Build769. A session run has now exercised the A26 runner with all three board builds and separate freshly formatted SD block images; the layer limits below still apply.

The SD I/O is board-specific and is not interchangeable:

- **SuperCard Lite:** Build define `SUPERCARD_LITE_IO`; SD data reads and writes use the 32-bit stream port at `0x09200000`. The model implements this path from an optional raw block image.
- **SuperChis:** Build define `SUPERCHIS_IO`; the conditional read code shares the `0x09200000` block-port implementation, while writes use the `0x09000000`/`0x0B000000` serial registers. Build769 programs eight NOR map entries with a three-write sequence and selects SRAM bank via mode bit 3. The published [SuperChis CPLD source](https://github.com/ChisBread/SuperChis/blob/e2b85b1533cf45d50ef1c5fafafefff200fca480/superchis.vhd) instead describes a four-write config sequence and a different SRAM bank selection path. Board revision equivalence is UNVERIFIED; details are in `docs/provenance/superchis-source-audit.md`. The runner tests the Build769 register transcript only and does not model NOR page reads or SRAM banks.
- **SuperCard SD:** Build define `SUPERCARD_FLASH_ADDRPERM`; the SD sector read path streams from `0x09100000` or `0x0B100000`, and writes use `0x09000000` or `0x0B000000`. Its internal flash address permutation is separate from SDRAM mapping. The model follows the SD assembly's 8-register LDM packing: it takes upper halfwords from every other transfer, so a 520-byte sector consumes 520 port reads. With the matching Build769 kernel, the selected-ROM run reaches `pl_normal` at `0x080062A2`; details and evidence limits are in `PROGRESS.md`. This is not physical-card qualification.

The source-derived SD traces differ by board. Lite and Chis each read 3,900 data-port values across 30 CMD18 reads (130 values per requested sector: 512 data bytes plus the 8-byte checksum); the SD build uses the `SUPERCARD_FLASH_ADDRPERM` alternate stream, which has different observed counts. The runner's source-shaped path completes 2,000 GBA frames for each profile. Latest runs: SD reported one block read and framebuffer FNV64 `30C994B7E348742D`; Lite and Chis reported 60 model blocks/3,900 port reads and FNV64 `357015EFA2DF90AB`. EWRAM execution began at global frame 47 for all three. Fixed-total-frame captures do not synchronize game state. Separate 64 MiB FAT32 images contain the matching KERNEL.GBA, plugin, and ROM, and pass `fsck.fat -n`: SD `8a4d3861e263f698340a661e1c38bfc87fce1c5597633b71baf03e442e61f3b2`, Lite `041a776efe8fe91299808a4f00aecd2f3db9a882f9e66b6712e85006f143a53d`, and Chis `af231ad09991c9ef925e2c2acf1bb4161208b49bf7222cba3bc020fd1825842f`. Shared plugin/ROM hashes are `cc868252fb113cd4160b8c6677d39cfe076056a4422f262b0975c99f5fb21de7` and `ad7bc56f0e4ae5938cc06f7cbd9be8a2cc8de715ca4a3eadfb057fd9d260afcb`; the embedded kernel hash is `7fa0e67e66345b05d6ffe9896c2dfc10f0095877e4b2cd8664ad13e15d999d24`. These mGBA results do not prove physical card timing, hardware behavior, GBA performance, or Atari correctness.

With `supercard-mgba-runner`, these runs establish only a source-shaped mGBA HLE path with synthetic card/storage behavior; they do not validate physical cards, SD timing, GBA performance, or Atari correctness. Chis NOR pages and SRAM banks are not modeled. Host tests cover SD read windows/lane packing, serial writes, and the Chis NOR-map write transcript. Physical SD response timing, card mapping/electrical behavior, Chis NOR page contents, and SRAM banking remain `UNVERIFIED`.

## Reuse existing DSSMM tests

DSSMM has native mGBA launch fixtures for all three EZ-FLASH release lanes. The fixture scripts live at the matching release commits, so switch the ignored clone to each profile's tag before running its suite. From `harnesses/third_party/dssmm/`:

```sh
git checkout v8.4.1
bash ezfomegade/scripts/test-native-launch-mgba.sh
git checkout v8.4.1-omega-test5
bash ezfomega/scripts/test-native-launch-mgba.sh
git checkout v8.4.1-blue-test5
bash ezfblue/scripts/test-native-launch-mgba.sh
git checkout 37c9e069c1f44c2d53ea633fa1bdcf97e788dcd4
```

These execute real launch UI/path/metadata code, but mock save, FAT transfer, patch, and card boot/page side effects. They are useful kernel regressions, not complete card or SD emulation. SuperFW has native menu/renderer tests and documents that they do not initialize physical SD, NOR, or cartridge SDRAM interfaces.

## Build context

DSSMM fixtures need devkitARM. Install and run the host toolchain by following [`WORKSPACE.md`](../WORKSPACE.md); this repository does not use Docker or a devcontainer. mGBA/Xvfb run on the host. Absolute workspace paths matter because fixtures generate absolute include paths. A previous `build-launch/` created under `/work` can leave stale `.d` dependencies; preserve/rename those generated directories before rebuilding under `/workspaces/a26.gba`.

The local mGBA/DSSMM source checkouts are ignored by Git. Do not commit mGBA, DSSMM kernel binaries, BIOS images, card firmware, or generated SD images.

`supercard-mgba-runner <kernel.gba> [frames [sd-image [capture.ppm [key-events]]]]` accepts a kernel image and optional raw SD block image, captures a 240x160 PPM, and accepts comma-separated GBA key events as one-frame taps (`600:0x1`) or inclusive holds (`600-610:0x1`). Masks use GBA key bits (`A=0x1`, `B=0x2`, `Up=0x40`, `Down=0x80`). Select the source-matched board using `A26_SUPERCARD_BOARD=lite|sd|chis` (default `lite`). For repeatable profile-layer runs, create separate block images and include that profile kernel with `KERNEL_GBA=<matching-kernel.gba> bash scripts/make-sd-image.sh work/a26-sd-<board>.img 64`, then pass the same kernel to the runner. Keep plugin and ROM file hashes identical across profiles, but record each image hash. Current kernel-in-image 2,000-frame results are recorded in `cards.json`; fixed-total-frame outputs are not synchronized game-state comparisons. These are synthetic mGBA results, not physical card behavior, game correctness, audio, or GBA timing. Source-derived SD responses and timing remain synthetic. `scripts/make-sd-image.sh` creates `SYSTEM/PLUG`, `SYSTEM/SAVER`, `SYSTEM/KERNELS`, and `ROMS`, matching the launcher's source-declared directory paths. ARM block transfers use `ARMCore.memory.loadMultiple`/`storeMultiple`; hooks must preserve upstream transfer behavior. mGBA's `struct mCore` layout depends on private compile definitions, so harness targets inherit `$<TARGET_PROPERTY:mgba,COMPILE_DEFINITIONS>`.
